Description

Every view you serve is a screen. Navigation is how you decide what those screens do to each other: which one the back gesture lands on, whether a result replaces the form that produced it, and how a reader leafs from page to page.

The split of responsibility is deliberate:

  • You own the journey. Only you know that a form has been consumed, that a step has been cleared, that a file is closed. To the client, a receipt is a view like any other.
  • The client owns the platform conventions. A back gesture always leads somewhere, an overlay never becomes a screen, and the entry point of your service always stays reachable.

So the protocol carries your *intent*, and the client turns it into stack behaviour. You never manipulate a stack: you do not know its state, and two clients (mobile, web) do not have the same one.

Fields Description

All navigation lives under the nav key of the served view.

FieldTypeRequiredDescription
nav.nextstringNoNext view of a paginated sequence. Absolute URL, or a path resolved against your service base URL
nav.prevstringNoPrevious view of the same sequence
nav.entrystringNoHow this view enters the stack: "push" (default) or "replace"

A bare token (step-two) is refused: on the wire it cannot be told apart from a relative path, and no client keeps a registry of view ids to resolve it against. Write /step-two — or the full URL.

How a view enters the stack

entry answers one question: must the user be able to return to the screen that led here?

ValueEffect
push (default)The view stacks on top of the screen that led to it. Back returns to that screen.
replace or 0The view takes that screen's place. Back skips over it.
-1, -2…It takes the place of the screens below as well: -n clears n+1. Back leads to whatever was left underneath.

A view returned in response to a form submission replaces that form, with nothing to declare. It is by far the common case — a receipt, a confirmation — and forgetting it produces a quiet defect: the user lands back on a form that has already done its work, and nobody notices during development.

The next step of a wizard must therefore declare push. A declared value always wins over this default. Forgetting it shows up immediately, on the first try: you can no longer walk back a step. Of the two possible omissions, this one gets caught; the other does not.

Everywhere else — a view reached through an action, a link, a deep entry — the default stays push. Declare replace on whatever acknowledges a completed action outside a form.

The number is counted from the current screen, in screens that are yours — never in absolute depth. The same view sits at different heights depending on the path taken (your catalogue, or a deep link), and you do not know which one the user took. If the top screen is at index T, the arriving view lands at T + entry.

The recoil always stops at your service's root, whatever the number. That is not a safety net: it is what makes a relative recoil safe at all, since one view can be served from several paths and never carry away more than exists. From the root alone, a recoil simply stacks.

A value above 1 is refused: stacking is stacking, and nothing more would be said.

entry places a new view. To return to a screen already visited — without reloading it, keeping the state it was in — use back, carried by a MessageView action.

The client cannot tell "here is your receipt" from "here is step 2": it applies the default for the situation — replace after a submission, stack elsewhere — and stands aside the moment you declare a value.

// Step 2 of a wizard: it comes from a submission, so it would replace
// step 1. Declare `push` so the user can walk back up.
const step2 = YeriaUI
    .createFormView('signup-step-2', 'Your details')
    .addTextField('city', 'City', true)
    .submitButton('Continue')
    .setEntry('push');

Paginated sequences

next and prev are siblings: the two arrows of a sequence, drawn by the client itself. You write two paths and get the same pagination on every screen, with no interface code of your own.

They are never bound to the back gesture. Back undoes time; pagination moves sideways.

setPage(current, total?) states where the view sits, and the client draws the indicator between the two controls — Page 2 / 4. Send numbers, not a sentence: the client formats them in the reader's language. Leave total out when the sequence has no known end, and the client shows the position alone. It is purely informative — moving still goes through setNext / setPrev, and a view that declares no position simply gets no indicator.

A page reached through those controls replaces the current one. Leafing through forty pages would otherwise stack forty screens and turn the back gesture into a tunnel. A page that declares entry: "push" still stacks, if you really want page-by-page back.

const page = YeriaUI
    .createReaderView('report-p2', 'Annual report — page 2')
    .addParagraph('…')
    .setPrev('/reports/annual/1')
    .setNext('/reports/annual/3')
    .setPage(2, 3);

What the client guarantees

These rules are not yours to change; count on them.

  • The root never moves. The view served by your service base URL sits at the bottom of the stack and never leaves it, so the entry point of your service stays reachable. A replace with nothing under it stacks instead.
  • A back gesture always leads somewhere. Reaching the root and going back leaves the service. No screen traps the user.
  • An overlay is not a screen. A MessageView is rendered as a dialog: it takes no stack entry and closing it navigates nowhere.
  • A deep entry gets its root. A link opening one of your sub-views directly (yeria://dl/v/{serviceId}?p=/orders/123, or the same link carried by a notification) mounts your base view underneath before showing the requested one. Expect one extra request, for your root.
  • Targets stay inside your service. next, prev and action targets are resolved against your service base URL; anything outside it is refused.

Not honoured today

setProcess() / belongsToProcess() — processId, processName, currentStep, totalSteps, stepName, canGoBack, canSkip — are carried on the wire and no client acts on them. No step indicator is displayed, and canGoBack does not change the back gesture.

They are kept so existing provider code keeps working, and this section will be removed once they are either implemented or dropped. Do not build a multi-step journey on canGoBack: use entry and your own navigation targets.
