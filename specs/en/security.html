Two signing mechanisms frame a Yeria service: you sign the views you return, Yeria signs the user tokens you receive. Both are verified, never assumed.

The two keys

Key Algorithm Owner Role
Platform key RSA (RS256) Yeria Signs user tokens. You only verify; the SDK fetches and caches the key by its kid.
Service key Ed25519 You Signs view envelopes and your calls to Yeria. The public half is registered; the private half never leaves your backend.

Generating an RSA keypair for your service is a mistake: the registry rejects anything that is not Ed25519.

The private key

It is your service's identity

Never commit it, never send it to Yeria, never ship it in a mobile build. Anyone holding it can sign views and calls as you. If it leaks, rotate immediately.

The signed envelope

app.serve(view) produces a v3 envelope:

{ "payload": "{\"type\":\"FormView\",…}", "signature": "…" }
i

The signature covers the bytes of the payload string, which is parsed afterwards. Never reformat the JSON once signed: verification would fail.

The app verifies the signature before rendering the screen. A view it cannot verify is refused — it is not rendered in a degraded form.

Verifying inbound tokens

Yeria is a registry and an identity provider, not a proxy: the app calls your URL directly. Verifying every token you receive is therefore your job.

const user = await app.verifyUserToken(bearer, process.env.YERIA_SERVICE_ID);

Passing your service id pins the audience: a token minted for another service is rejected. The platform key is fetched once and cached, so later verifications make no network call.

!

The SDK ships helpers, not middleware. There is no YeriaApp.authMiddleware(): wiring it into your framework stays your call.

Key rotation

On an already approved service, changing the public key is a registry edit: it is staged as a draft and applied when the review is approved. Emergency rotation, after a leak, follows a separate path described in Provider integration.

Transport and exposure

  • Your backend must be reachable over HTTPS from user devices.
  • No business data transits through Yeria: traffic goes from the phone to your server.
  • Views carry an expiry; an expired view is refused by the app.
